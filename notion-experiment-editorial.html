Notion Slash Commands Study

Notion's slash command shortcut only works on desktop. I ran an 8-person timed experiment comparing it against the mobile "+" button to measure whether that gap actually costs users time and accuracy.

Duration

2 weeks

Role

Researcher, sole author

Method

Within-subjects experiment, 8 participants

Tools

Notion, Excel, paired T-test analysis

Hero image, split screen of Notion's desktop slash command menu next to the mobile "+" button flow

The short version

Mobile users took 60% longer than desktop users to do the exact same Notion tasks.

On desktop, typing "/" and a keyword builds a Notion block instantly. On mobile, the same action means tapping a "+" button, scrolling a menu, and tapping again. I had 8 existing Notion users build the same page twice, once with each method, and timed every step.

Context

Notion's signature shortcut exists on desktop only, and nobody seemed to be asking why.

Typing "/" followed by a keyword, like /page or /todo, is Notion's defining feature: it builds a block instantly with no mouse required. That shortcut is available on desktop and web. On the iOS and Android apps, the same block types exist, but only behind a "+" button and a scrollable menu. The keyboard shortcut never made the jump to touch.

I couldn't find any public discussion of this gap from Notion or its users, which made it worth measuring rather than assuming it was harmless.

Side by side, desktop slash command menu vs. mobile "+" button menu

Two paths to the same block: one keystroke on desktop, three taps on mobile.

How I tested it

Each of the 8 participants completed the same 5 tasks twice, once per input method.

Every participant already used Notion regularly, so the study measured input method, not learning curve. Each person completed 5 tasks, creating pages, headings, lists, embeds, and quote blocks, first with slash commands on desktop, then again with the mobile UI. Half the group started on desktop and half on mobile, to rule out practice effects.

3 of the 5 tasks required switching between typing and tapping mid-task, which is the exact friction slash commands are built to remove.

What I found

The slower a task was on mobile, the more mode-switching it required.

Simple, single-step tasks barely differed between desktop and mobile. Tasks that forced someone to pause typing and go find a button showed the largest gap in both time and errors. A paired T-test on the full data set confirmed both differences were statistically significant, not chance: p = 0.0007 for time, p = 0.0006 for errors.

What people said

Every participant preferred typing the command. Most hadn't known it was there.

In the post-test interview, 100% of participants said desktop let them work faster, and 87.5% called the keyboard shortcut more comfortable and intuitive than tapping through the menu. Half said, unprompted, that they wished slash commands worked on mobile too.

Limitations & what's next

8 participants is enough to see a pattern, not enough to build a feature on.

Mobile's higher error rate likely inflated its completion times too, since fixing a mistake takes time of its own, so the study can't yet fully separate slower input from error recovery. The sample also leaned toward existing desktop users, and forcing a hard choice between input methods doesn't reflect how people actually mix keyboard, mouse, and touch day to day.

01

Isolate input method from platform

Run both conditions on mobile only, a Bluetooth keyboard against the "+" button, so platform is no longer a variable.

02

Recruit a mobile-first sample

This group leaned desktop already. A mobile-native group of Notion users may show an even larger gap, or a smaller one.

03

Design for fewer pauses, not a literal slash

The value isn't the "/" character itself, it's skipping the menu. A mobile equivalent just needs to cut how often someone has to stop typing to find a button.

Reflection

The most useful outcome of this project was learning to design the study itself.

The real lesson wasn't really about Notion, it was how much a study's design shapes what it's able to prove. Counterbalancing the task order and giving every participant the same reference sheet were both deliberate attempts to stop ordinary noise from being mistaken for a real result. If I ran this again, I'd test both input methods on the same platform from the start, so the finding needed no caveats about desktop familiarity at all.
