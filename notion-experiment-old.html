Do slash commands make Notion faster? A controlled experiment.

Notion lets you type "/" to instantly create anything in a document — a to-do list, a heading, an image — without touching your mouse. It's one of the app's most-loved shortcuts. But it only works on desktop. On mobile, the same actions take several taps through menus instead. I ran an 8-participant, within-subjects controlled experiment to find out whether that missing mobile shortcut actually costs people time, or whether it's just a nice-to-have that nobody would really miss.

Long story short

When compared to keyboard slash commands on desktop, Notion's mobile users took 60% longer to complete tasks and made more than double the mistakes.

I had 8 Notion users build the same simple Notion page twice: once using keyboard "/" commands on a laptop, and once tapping through menus on their phone. The laptop version was faster every single time, for every single person — and the gap was large enough that it almost certainly wasn't luck.

Context

Notion has a fast way to work — but only on half its platforms

Notion is a notes and productivity tool built around typing. Its defining feature is the slash command: type "/" followed by a keyword — /page, /todo, /quote — and Notion creates that block instantly, no mouse required. It's available on desktop and web. On the iOS and Android apps, the same actions exist, but only behind a "+" button, a scrollable menu, and a tap — the keyboard shortcut never made the jump to mobile.

That gap raised a question I couldn't find a confident answer to anywhere: is typing "/" actually faster than tapping a button, or does it just feel that way to power users who already know the shortcuts? I decided to test it properly instead of guessing.

Caption. The reference infographic given to all participants before the study — equalising prior knowledge of keyboard shortcut and mobile button locations.

Research question

Does using keyboard slash commands in Notion allow users to complete tasks faster than using UI buttons and touch gestures on mobile?

Notion's desktop users can trigger any feature without lifting their hands from the keyboard. Mobile users can't. The question is whether that difference shows up in the data.

Hypothesis

H1 — Alternative hypothesis

When creating inputs in Notion, slash commands let users complete tasks faster than UI buttons and gestures.

H0 — Null hypothesis

They make no difference.

I treated H0 as the default. The data needed to clear standard significance thresholds (p < 0.05, 0.01, 0.001) before I'd reject it — rather than assume my hunch was right going in.

🔬   How might we find out whether slash commands are genuinely faster — or whether they just feel that way?

Study design

A within-subjects design — so every participant was their own control group

I recruited 8 participants who already used Notion and were self-reportedly comfortable with both keyboards and touchscreens — this was a test of input method, not a test of who could learn Notion fastest. Choosing a within-subjects design meant the same person completed all tasks in both conditions, which controls for individual differences in typing speed, dexterity, and general tech comfort, and allowed me to directly compare each participant's performance across both platforms.

Participants used only the keyboard and slash commands to create embeds, headings, new pages, and more. No mouse or UI buttons permitted for task completion.

📋

Study structure

Each session had three parts: a pre-test questionnaire (consent + baseline familiarity), the timed experiment across both conditions, and a post-test questionnaire capturing subjective preferences and reflections.

📄

Standardised instructions

All participants received an identical digital task instruction sheet containing 5 tasks, ensuring the same exact steps were performed each time across both conditions.

🗺️

Reference guide provided

A keyboard layout and UI button reference infographic was given before starting the study, so prior shortcut knowledge wouldn't skew results across participants.

👤

Within-subjects design

Every participant completed both conditions, controlling for individual differences in typing speed, dexterity, and general tech comfort — each person was their own control.

🔀

Counterbalancing

Half the participants started on desktop, half on mobile — so practice effects and platform fatigue couldn't quietly favour one condition over the other.

⚠️

Defining participant errors

Errors meant typos, mis-clicks, or incorrect output — not slow typing or thinking time. Recorded live with a stopwatch and verified against session recordings made with participants' consent.

Task design

Five tasks, varying in complexity and mode-switching demand

Tasks were calibrated to test a range of complexity. Simple tasks (1, 3) had few steps and no mode-switching. Complex tasks (2, 4, 5) required pausing mid-typing to switch between keyboard and interface — the exact friction slash commands are designed to eliminate.

01

Make a new page Low complexity

Desktop: type /page, press Enter, name it. Mobile: tap +, select Page, name it. Quick and straightforward — no mode switching required on either platform.

02

Add a toggle list with a to-do list inside High complexity

Desktop: type a toggle, then /to-do inside it, add 5 items, close. Mobile: tap + for toggle, then + again for to-do inside, repeat per item. Multiple mode switches per iteration on mobile.

03

Create a heading Low complexity

Desktop: type /heading 2, press Enter, type "Meeting Agenda". Mobile: tap +, select Heading 2, type text. The simplest task — and the one that showed the smallest performance gap.

04

Embed an image from a URL High complexity

Desktop: type /embed, paste the provided URL, press Enter. Mobile: tap +, locate Embed, paste URL, tap Embed link button. On mobile, participants had to switch apps to copy the URL — producing the largest gap of any task (p < 0.001).

05

Add a quote block with bold text High complexity

Desktop: type /quote, enter text, select with trackpad, press Cmd/Ctrl+B. Mobile: tap +, select Quote, type text, press and hold to select words, tap B. Touch text selection was a common source of both errors and delays.

Some struggled a lot; others less so. The desktop experience was both faster and more predictable.

Statistical validation

Paired T-test: the null hypothesis is confidently rejected

With only 8 people, a faster average on desktop could just mean I happened to recruit 8 fast typists. To rule that out, I ran a paired two-tailed T-test — a standard check that asks "how likely is it that this gap happened by chance?" If the answer is "very unlikely," the difference is real. If not, it's not safe to draw conclusions from it. The overall time difference passed that check easily. But I didn't stop at the overall number — I ran the same check on each of the 5 tasks individually, because an average can hide a lot.

Task time — T-test result

P = 0.000657

Below 0.001. There is a 0.1% or less probability this difference is due to chance. Null hypothesis confidently rejected.

Error rate — T-test result

P = 0.000589

Also below 0.001. Slash commands were associated with significantly fewer errors too — though this wasn't the primary hypothesis.

Limitations

I can't fully separate "faster input" from "fewer mistakes"

Mobile was both slower and more error-prone — participants made more typos and wrong taps there than on desktop. Fixing a mistake takes time. So when I say "mobile took longer," some of that extra time might really be "mobile caused more mistakes, and fixing mistakes takes time" — not the input method itself being slower. With only 8 people, I can't cleanly separate those two explanations from each other.

⚡

Error-time confound

Higher mobile error rates likely inflated mobile completion times — the study design can't yet isolate how much of the gap is input speed versus error recovery time.

👥

Small sample

8 participants gave the total-time and total-error results real statistical weight, but left individual-task comparisons more vulnerable to noise. One or two mis-taps could swing a task's P value.

🌍

Ecological validity

Real Notion users mix keyboard shortcuts, mouse, and touch as they like — this study forced a binary choice that doesn't reflect daily use.

💻

Prior platform familiarity

Most participants already used Notion primarily on a laptop — desktop may have had an advantage independent of the input method itself, simply through greater familiarity.

Recommendations

What comes next

Recommended next steps

01

Conduct a follow-up study with both conditions on mobile — one using slash commands via Bluetooth keyboard, one using the + button UI — to isolate the input method variable from the platform variable entirely.

02

Recruit a larger, more mobile-first sample. This study's participants were primarily desktop Notion users — a mobile-first group may show meaningfully different patterns.

03

Only consider implementing slash commands on mobile once the above studies provide clearer, more isolated evidence. The current data supports the direction, but isn't strong enough to build on alone.

A design direction for mobile

The core value of slash commands isn't the slash — it's eliminating mode-switching. Instead of stopping typing to reach for the mouse or hunt through a menu, the user stays in one continuous input mode.

A mobile equivalent doesn't need to look like a slash command. It just needs to solve the same problem: reducing the number of times a user has to pause, switch interaction modes, and navigate a menu to create a single content block. The question for Notion's mobile team is what that looks like when there's no keyboard always present.

Reflection

Designing a fair test was harder than running one

On study design

The most valuable lesson wasn't a finding about Notion — it was understanding how much a study's design shapes its conclusions. The within-subjects structure, the counterbalancing, the reference infographic, the standardised instruction sheets: each was a deliberate attempt to control for something that could otherwise silently corrupt the data. Without them, any result would have been noise dressed up as signal.

On reading results carefully

Task 4 showed a P value below 0.001 and a massive time difference — but much of that gap came from participants having to switch apps on mobile to copy a URL. That's a confound specific to the task setup, not a pure test of input methods. A cleaner study would have pre-provided the URL in the clipboard, and I'd make that change in the next version.

What I'd do differently

Run a follow-up where both conditions are on the same platform (mobile), varying only the input method. That would isolate what I was actually trying to test, and produce something far more actionable to hand to a product team.
